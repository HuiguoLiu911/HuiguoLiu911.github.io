The question

The first hands-on exercise in MSBA 6155 (Generative AI) was to wire a chat model to a document so that answers come from the document rather than from the model’s memory. The point was less the chatbot and more the plumbing: how retrieval-augmented generation is assembled from loaders, splitters, embeddings, a vector index and a chain, and how a classroom Azure AI Foundry deployment is called from code without leaking credentials.

Data

There is no dataset. The repository tracks a 436-byte synthetic sample text written for the class so the app can be demoed immediately, and any other PDF or TXT dropped into the data folder is ignored by git. Generated FAISS indexes are also ignored.

Method

I wrote the app as five small modules so each stage can be swapped independently:

  • document_processor.py loads PDF or TXT with PyPDFLoader / TextLoader and splits on newlines with CharacterTextSplitter(chunk_size=1500, chunk_overlap=300).
  • embedding_indexer.py embeds chunks with AzureOpenAIEmbeddings (text-embedding-ada-002) and builds an in-memory FAISS index, with save and load helpers.
  • rag_chain.py is an LCEL chain: retriever with k=5, a formatter that concatenates the chunks, a prompt that tells the model to answer only from context and to say “I don’t know” otherwise, and gpt-4o-mini at temperature 0 with a 2000-token cap.
  • chatbot.py wraps the chain and keeps conversation history.
  • ragapp.py is the Streamlit UI: file uploader, a cached chatbot keyed on the file bytes so repeat questions do not re-embed, a chat-message loop and a clear-history button.

Two details took the most debugging. The chat model is reached through the OpenAI-compatible /openai/v1 base URL while the embedding model needs the native Azure endpoint, so the indexer strips the suffix. And all four configuration values (key, base URL, chat deployment, embedding deployment) are read from environment variables via python-dotenv; the repo ships only a placeholder .env.example. Two standalone smoke tests check the Azure connection for a chat completion and a multimodal image-description call.

Results

  • A working end-to-end RAG app: upload, chunk, embed, index, retrieve top 5, generate, chat UI with persistent history.
  • Grounding by design: temperature 0 and a context-only prompt that instructs the model to say “I don’t know” when the document does not cover a question.
  • Cost per question is a few hundred gpt-4o-mini tokens plus one embedding pass per uploaded document.
  • No quantitative evaluation of retrieval accuracy or latency was part of the assignment, so none is claimed.

What it changed

This was an individual classroom exercise with no slides or report. Its value for me was a clean, modular RAG template for the two larger course projects that followed: the Resume–JD Copilot reuses the same document-processor, FAISS-indexer and chain module shapes with guardrails added, and the Sponsor Intake Copilot uses a simpler weighted-cosine variant of the same retrieval idea.

Limitations and next steps

It requires a live Azure key and has no local-model fallback. The index lives in memory per session; the save and load helpers are not wired into the UI. Only one PDF or TXT at a time. Splitting on newlines means very long paragraphs can exceed 1500 characters. Chat history is stored but not fed back into the prompt, so each question is answered independently. There are no automated tests. Natural next steps are a recursive splitter, conversational memory in the chain, and a small retrieval-quality check set.
